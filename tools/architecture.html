End-to-End View

From Wallet Intent to an App Ecosystem

Participant wallets initiate proposals and identity-bearing actions. The validator cluster, release-flow governor, and IPFS-backed replication establish canonical Oak and JCR-backed state. From there the system now splits cleanly into two edge-facing planes: a read-model fabric for posture and explorer truth, and a governed runner control plane for staircase launches, persisted inputs, normalized events, and indexed artifacts.

Wallets Validators Oak/JCR State Release Flow Read Plane Runner Plane Apps

Canonical Truth

Validator Network and State

The validator cluster, not any single app, is the source of truth. Raft term, release-flow state, confirmations, replicated Oak state, and the blockchain-backed JCR reality all originate there.

Platform Layer

Dual Edge Planes

Apps do not read raw validator internals directly. The read plane projects canonical state into app-safe contracts such as /ops/v1 and oak-chain-action, while the runner plane exposes governed staircase APIs for suites, runs, inputs, events, artifacts, and cancel semantics.

Flow

State Propagation Pipeline

Each layer narrows the system from canonical consensus state into reusable read models and then into fast-moving application surfaces.

Participants

Wallet Intent

Participant wallets carry identity, sign proposals, and introduce work into the mempool and confirmation path.

  • Wallet ownership and signing
  • Proposal ingress and confirmations
  • Release eligibility begins here

Consensus

Validator Network

Validators, leader election, release-flow stages, and replication create the canonical Oak state and blockchain-backed JCR truth the rest of the system must respect.

  • Leader and follower roles
  • Raft term, queue, and governor state
  • IPFS-backed durability and replicated content state

Edge Plane

Read Adapter and Runner Control Plane

One edge lane converts consensus posture into dashboard-safe read models, while a second runner lane governs staircase execution against infra harnesses and persists durable run truth outside the validator plane.

  • /ops/v1 and oak-chain-action for read-only posture, explorer, and signal clients
  • /runner/v1 for suites, test runs, events, artifacts, and cancel semantics
  • Cloudflare and Adobe I/O read paths, with a separate staircase runner worker for mutable test orchestration

Apps

App Ecosystem

EDS pages, Oak Ops, Staircase, DA/live properties, and future explorers render specialized views of the same underlying truth while keeping consensus authority separate from UX concerns.

  • Oak Ops read-only control surface
  • Staircase validation flight deck with persisted run records
  • Genesis-state, provenance, and content-state explorers

Write Path

Canonical State Movement

  1. Participant wallet signs and submits intent.
  2. Validators ingest proposals into mempool and confirmation stages.
  3. Release-flow governor advances, holds, or overflows work based on cluster posture.
  4. Replication and IPFS-backed durability make the state globally recoverable.

Read and Control Paths

Projected State and Governed Test Control

  1. Edge adapters read consensus and explorer sources and normalize them into stable posture contracts.
  2. The runner worker governs staircase attach, launch, cancel, and artifact indexing without exposing raw infra scripts directly to the browser.
  3. Oak Ops fetches read-only cluster truth, while Staircase reads and writes only against the runner contract.
  4. Each app expresses one slice of value without coupling directly to validator internals or shell scripts.

Trust Boundary

The dashboard never writes validator consensus directly. Oak Ops stays read-only through the ops adapter, while Staircase talks to a separate runner contract that supervises infra automation and persists normalized run records outside the consensus plane.
